## Part 2 — Threat Analysis

### T-1: Boilerplate Corpus Poisoning via Adversarial Document

**Description.** An attacker plants a document containing text designed to match the boilerplate-detection machinery's threshold across the entire corpus. The boilerplate detector is defined in §6.2 as "text repeated across many documents in the corpus" with no user configuration required. The detection uses dedup machinery (text fingerprint + occurrence count). If an attacker can introduce a document whose header or footer text matches existing high-value content verbatim, or — more subtly — pre-poisons the corpus by uploading many near-identical documents whose shared text reaches the boilerplate threshold, that content gets classified as `boilerplate` tier across the corpus. Default retrieval excludes boilerplate. The high-value content disappears from retrieval results corpus-wide without any individual document failing quality checks.

**Feasibility.** Medium-high for insider threat or supply-chain attack (the attacker controls documents entering the KB). Low for external attacker with no upload access. The threshold (OQ-8 proposes 30% of corpus documents) means an attacker needs to control a third of the document corpus for a fully-loaded KB, but for a small or new KB this could be a handful of documents. The segment-taxonomy.md §4.4 "conflict rule" states class description wins over boilerplate detection — but only if the user has provided a class description.

**What the design permits.** No anomaly detection on boilerplate reclassification at corpus level. A large fraction of previously `primary` segments being reclassified to `boilerplate` in a single ingest will not trigger any alert as designed. The pre-promotion validation gate checks chunk count bounds (±20%) but this attack does not reduce chunk count — it changes salience tiers only.

**Mitigation.** Add a pre-promotion validation gate (§10.4 Gate 2 extension): compare the salience-tier distribution of the shadow collection against the prior live collection. A shift of more than a configurable percentage of `primary` segments to `boilerplate` blocks promotion and raises an alert. Additionally, boilerplate detection thresholds should be per-segment-class, not corpus-wide, so class descriptions can anchor a class against corpus-level poisoning.

### T-2: Permission Laundering via Connector Gap

**Description.** A connector (SharePoint, Google Drive, Confluence) is configured against a source system where the connector's service account has read access to restricted folders that the KB's intended users do not. At ingestion time, the connector collects these restricted documents. If `permission_fidelity=unavailable` (the connector cannot retrieve per-document ACLs, only corpus-level access), the `acknowledged_permission_gap=true` flag allows ingestion to proceed. All collected content is ingested with `permission_mode=public_to_kb`, making it retrievable by anyone with KB access. A restricted HR policy or legal document is now answerable to all KB Viewers.

**Feasibility.** High. This is the exact scenario §14.3 names as the failure mode to prevent. The connector-gap acknowledgement path is explicitly supported by the design. A misconfigured or over-permissioned service account is a common enterprise deployment error. The design requires acknowledgement but does not restrict what content enters under `unavailable` fidelity — it trusts the operator.

**What the design permits.** As currently specified: (a) `acknowledged_permission_gap` is optional on `SourceRun` (S-R2 finding), meaning it could be False while the ingestion proceeds; (b) there is no maximum-fraction-unavailable guard — a KB where 100% of documents have `permission_fidelity=unavailable` is allowed; (c) no re-notification after the initial acknowledgement if subsequent re-collections add new restricted content under the same gap acknowledgement.

**Mitigation.** (1) Fix S-R2 (make acknowledgement required and propagate to TenancyBlock). (2) Add a per-collection maximum-unavailable-fidelity cap: if more than a configurable percentage of chunks in a KB have `permission_fidelity=unavailable`, the KB is flagged in the UI with a persistent "permission fidelity warning" visible to all KB Viewers at query time. (3) Re-acknowledgement required when a re-collection adds new documents under an `unavailable` fidelity connector — the prior acknowledgement does not cover newly discovered content.

### T-3: Injection Suspicion Score as Content Suppression

**Description.** The `injection_suspicion` score is a `float [0,1]` computed at Decompose, stored in provenance, and described as "retrievable and filterable" and "never used to silently exclude." A caller — either a retrieval client or the KB Editor configuring `retrieval_treatment.confidence_floor` — could set a filter that excludes high-suspicion chunks from default retrieval. This is explicitly a supported use case. However, the same mechanism can be weaponised: if an attacker can reliably predict what text patterns trigger high `injection_suspicion` scores, they can embed those patterns in documents covering legitimate topics — causing the classifier to assign high suspicion scores to legitimate content and effectively hiding it from retrieval. The victim is a retrieval client that applies a suspicion-score filter to protect against prompt injection, but now also suppresses legitimate high-value documents.

**Feasibility.** Medium. Requires the attacker to know or infer the injection-pattern detection heuristics. The design does not specify what patterns trigger suspicion (by design — keeping them non-public helps), but a determined attacker can probe via document uploads. The platform's policy of "never silently exclude" does not protect against a caller who explicitly filters on suspicion score.

**What the design permits.** The retrieval API supports per-request filter overrides within KB-config limits (§11.2: "per-request override of retrieval strategy within limits set by the KB config"). A caller who sets `injection_suspicion_max: 0.0` will exclude any flagged chunk. The design neither recommends against this pattern nor warns about its abuse potential.

**Mitigation.** (1) In the MCP tool description (§14.1 MUST: "the MCP tool description states the trust level"), also state that applying high-pass injection suspicion filters as a content-exclusion policy may suppress legitimate content if the injector can predict the detection heuristics. (2) Add observability: track the rate of suspicion-filtered chunks per query session; a session that consistently receives zero results due to suspicion filtering but whose queries would otherwise return many results is flagged in the operator dashboard. (3) Document in the retrieval API reference that `injection_suspicion` is an advisory signal, not a trust verdict, and that callers relying on it as an access-control gate should pair it with human review of the flagged documents.

## Part 3 — Verified Sound

The following design elements were reviewed and found to correctly implement the relevant spec requirements:

1. **TenancyBlock present in all six contracts from Phase 0** (contracts/README.md shared blocks, confirmed in all six contract pages). The Phase 0 MUST requirement (§19, M-095) is correctly anticipated.

2. **Trust label `trust_level=untrusted_ingested` present on every chunk** (contracts/README.md Provenance block). The single-enum approach correctly implements §14.1's "mark content as retrieved untrusted material" with forward-extensibility noted. §18.3 test 9 and §11.4 MCP tool description requirement are correctly wired.

3. **Invisible-content detection at parse time with hidden text retained, not stripped** (contracts/parse-result.md `InvisibleContentDetection`, contracts/README.md Provenance block `invisible_content_flags`). Correctly implements §14.1's "detected and flagged" with the "labelled not sanitized" invariant. The `text` field in `InvisibleContentDetection` retains the hidden text.

4. **Injection suspicion score end-to-end propagation** (contracts/parse-result.md → segment-set.md `Segment.injection_suspicion` → contracts/README.md Provenance `injection_suspicion`). The score is present and required (`yes, 0.0 if none`) at segment and chunk level, is filterable, and is explicitly stated as never used for silent exclusion. §18.3 test 9 is correctly addressable.

5. **Ingestion-time LLM calls treat document content as data** (architecture/provider-abstraction.md §4.3, §4.4). The prompt-structure discipline (XML delimiters, system message framing, schema-validated JSON output) is specified for all four operations. The `review_status` field on eval questions cannot be set to `reviewed` by LLM output — it requires authenticated human action. §14.1 MUST requirement M-067 is covered.

6. **Secret-free ingestion config by construction** (contracts/ingestion-config.md `EmbeddingConfig.provider` is a name, not a credential; `secret_free_attestation: bool (const true)`; architecture/provider-abstraction.md §6.1–6.4). Provider references are by name only; credential lookup is separate. The export pipeline specifies placeholder replacement and `requires_credentials` field. §14.2 M-071 is covered at the schema level (runtime defense-in-depth gap noted in S-R7).

7. **Permission fidelity levels representable at sufficient fidelity** (contracts/inventory.md `SourcePermissions.fidelity: enum{authoritative, best_effort, unavailable}`, `TenancyBlock.permission_fidelity`). The three-tier enum correctly represents §14.3's spectrum including the explicit `unavailable` acknowledgement path (gaps in enforcement noted in S-R2; the representability itself is sound).

8. **Tombstone log append-only, never truncated** (architecture/index-lifecycle.md §10.5). The design explicitly states "the tombstone log is never truncated, even after all known copies of the deleted content have been destroyed" — this correctly supports right-to-erasure audit trails.

9. **Purge vs. delete distinction visible in UI** (architecture/index-lifecycle.md §12.2 table). The two-row table distinguishing scope and snapshot treatment, with the statement "An operator cannot present the first as the second", correctly implements §17.1 M-089.

10. **Cold snapshot restore requires tombstone replay before promotion eligibility** (architecture/index-lifecycle.md state machine `TOMBSTONE_REPLAY → VALIDATING`, §10.4 step 3). The state machine enforces that `TOMBSTONE_REPLAY` must complete before `VALIDATING`. This is mandatory and not skippable as designed, satisfying §17.1 M-087.

11. **Eval set `review_status` has no default** (contracts/eval-set.md). Correctly implemented as "yes, NO DEFAULT" with explicit statement that omission is a construction error. Provisional status is therefore structurally inseparable from the data (§9.2 M-043).
