| **C-R1** | segment-taxonomy.md §2.1 (`boilerplate` row); contracts/README.md (TransformationRecord); contracts/chunk.md (Invariants) | **blocker** | **Boilerplate-strip is Tier 1 but Tier 1 is not allowed to change chunk text — the three documents are jointly incoherent.** The taxonomy states: "Tier 1 transformation default-strips boilerplate *from the text field* but retains it in provenance so it can be restored." The TransformationRecord contract states: "`changed_text` MUST be `false` for every Tier 1/Tier 2 op; only a Tier 3 op may set `true`." chunk.md states: "Chunk text is byte-identical to source unless a `tier=3, changed_text=true` transformation is recorded." If `boilerplate_strip` is a Tier 1 operation that removes text from the served field, it must set `changed_text=true`, violating the TransformationRecord constraint. If `changed_text=false`, the chunk text is unchanged — contradicting the taxonomy's "strips from the text field." A chunk cannot simultaneously be byte-identical to source (the contract) and have its text stripped (the taxonomy). Furthermore, chunk.md's golden-corpus note "text still byte-identical (Tier 1 cleanup is recorded but `changed_text=false`)" does not address the boilerplate-strip path at all, leaving it unresolved. | Resolve the intent in a single authoritative place. The recommended fix: `boilerplate_strip` does NOT modify `chunk.text`; it is a salience-tier signal only. Boilerplate segments are indexed with byte-identical text and default-excluded from retrieval via the `boilerplate` salience filter. Remove "strips boilerplate from the text field" from the taxonomy's boilerplate row; replace with "Salience tier is `boilerplate` by default; segment text is retained byte-identical in the chunk; default retrieval filter excludes `boilerplate` tier." Update the TransformationRecord note to clarify that `boilerplate_strip` is a classification input, not a text-modifying operation. |
| **C-R2** | contracts/chunk.md (golden-corpus note, line ~198); contracts/README.md (TransformationRecord); segment-taxonomy.md §2.1 (`scanned_region` row) | **blocker** | **"Tier 1 OCR cleanup is recorded but `changed_text=false`" is self-contradictory for scanned content.** chunk.md's golden-corpus worked example states: "text still byte-identical (Tier 1 cleanup is recorded but `changed_text=false`)." OCR cleanup is listed in ingestion-config.md as a Tier 1 operation (`ocr_cleanup`). For a `scanned_region`, the "source text" is the raw OCR output. If OCR cleanup corrects OCR character errors, normalizes whitespace, or repairs encoding in that output, the resulting text is not byte-for-byte identical to the raw OCR string. Setting `changed_text=false` on an operation that materially alters the text string is a false assertion in provenance — exactly the traceability failure the system exists to prevent. The design does not define what "source text" means for a scanned region (the PDF scan image cannot be "text-identical"), leaving implementers to guess. | Add a definition: for `scanned_region`, "source text" is the raw OCR string as emitted by the OCR engine before any platform processing. Clarify in the TransformationRecord spec that OCR cleanup operations that alter the text (character correction, encoding repair) MUST set `changed_text=true` with `tier=1`. Update §12 chunk invariant to read: "Chunk text is byte-identical to source unless a `changed_text=true` transformation is recorded — whether tier 1 or tier 3." Revise the golden-corpus note to remove the incorrect `changed_text=false` claim for OCR cleanup. |
| **C-R3** | segment-taxonomy.md §4.1–§4.3; contracts/segment-set.md (`Segment.salience_basis`) | **blocker** | **`salience_basis` enum cannot represent 5 of the 9 taxonomy signals, making the "all firing signals recorded in provenance" promise unimplementable.** The taxonomy §4.3 states: "Lower signals are recorded in provenance as contributing evidence even when they do not win." Nine signals are defined. `Segment.salience_basis` in segment-set.md is `enum{class_description, boilerplate_detection, structural_position, override}` — four values. Missing signals that cannot be recorded: (1) `explicit_user_exclusion`, (2) `unservable_detection`, (3) `ocr_confidence_floor` (the `excluded` assignment from OCR below threshold), (4) `segment_type_prior`, (5) `no_signal` (the default). A chunk produced from an OCR-below-floor segment has no way to record that its `excluded` tier came from the OCR confidence signal; `override` is the closest match but is semantically wrong (it means a human override). This renders §6.3's explainability goal and the explain-mode requirement (§11.5) partially unimplementable. | Replace the four-value enum with a richer structure that mirrors the taxonomy's signal list: `enum{explicit_user_exclusion, unservable_detection, ocr_confidence_floor, ocr_confidence_warning, class_description, boilerplate_detection, segment_type_prior, structural_position, default_supporting}`. Also add a `salience_signals_fired: list[salience_basis]` field to record all contributing signals (not just the winner), as required by taxonomy §4.3. |
| **C-R4** | contracts/segment-set.md (Open Question 1); contracts/chunk.md (Deterministic chunk ID derivation) | **blocker** | **`segment_path` canonical format is unresolved but load-bearing for Phase 1.** chunk.md uses `segment_path` as one of five canonical inputs to chunk ID derivation: `"\x1f".join([document_id, content_hash, config_version, segment_path, str(chunk_index)])`. segment-set.md Open Question 1 flags: "`segment_path` construction... must be pinned before Phase 1." The proposed default `"/".join(structural_path) + "#" + within_heading_ordinal` has not been approved. Without a pinned format, two implementations of Build will produce different chunk IDs for the same segment, making orphan detection, replace-by-document, and resumability unreliable. The ADR-0006 reference in both documents points to a decision that depends on this pinning. | Pin the `segment_path` format in ADR-0006 as a closed decision before Phase 1 implementation begins. The proposed default is a reasonable starting point; the key action is marking it as a closed decision, not an open question. Document edge cases: heading-less documents (structural_path empty → segment_path = `#0`, `#1`, …); nested tables (compound path as per OQ-9 proposed default); cross-document references (the referenced segment's path from its own document). |
| **C-R5** | contracts/segment-set.md (Open Question 2); segment-taxonomy.md §2.1 | **major** | **segment-set.md Open Question 2 proposes type names that the taxonomy has already superseded.** segment-set.md OQ-2 states: "Proposed default: the §6.3 seed list plus `scanned_region`, `revision_block`, `chart_commentary`." The ingestion-config.md `ClassRule.segment_class` enum, the Provenance block's `segment_type` enum, and the classification LLM output schema (provider-abstraction.md) all depend on a single, agreed type set. | Close segment-set.md OQ-2 by replacing its proposed list with a forward reference to segment-taxonomy.md as the definitive type list. Confirm that the classification operation in provider-abstraction.md §4.3 references segment-taxonomy.md for its output schema (the note "see docs/contracts/chunk.md for the taxonomy" should be "see docs/architecture/segment-taxonomy.md"). |
| **C-R6** | contracts/chunk.md (`text` field); contracts/segment-set.md (`Segment.text`); segment-taxonomy.md §2.1 (`figure_region` row); segment-taxonomy.md §3.2 (indexing invariant) | **major** | **`figure_region` segments have null `text` but `chunk.text` is a required field — the indexing invariant and the chunk contract are irreconcilable for visual segments.** The taxonomy states (§3.2): "Everything is indexed. Tier controls default retrieval behaviour only." segment-set.md's `Segment.text` is optional: "Null only for non-text segments (e.g. figure whose caption is separate)." But chunk.md's `text` field is required (`yes`). If a `figure_region` segment produces a chunk, that chunk must have a non-null `text` — but there is no source text to satisfy byte-identity. If `figure_region` does not produce a chunk (taxonomy OQ-2 proposes "no vector is generated for the figure itself"), then it violates the "everything is indexed" invariant. The recommended resolution: `figure_region` segments are represented in the segment set (satisfying reassembly) but do not produce chunks when no textual content (caption or generated description) is available. Mark the `chunk.text` field as "required unless segment type has no textual representation" and define the closed list of such types (`figure_region` without a generated description, and any type where `segment.text` is null). | **C-R7** | contracts/chunk.md; spec §7.2 (Tier 3 MUSTs) | **major** | **The chunk contract provides no field to store the Tier 3 original text, violating the §7.2 MUST "original always retained" and "visible at citation time".** §7.2 requires for Tier 3: "Original always retained, never overwritten" and "Rewritten chunks flagged in provenance and visible at citation time." When `tier=3, changed_text=true`, `chunk.text` contains the rewritten form. The caller receives the rewritten text. The original text is accessible only by fetching the source document from object storage via `provenance.source_location`. This is not "visible at citation time" in any immediate sense — it requires an additional retrieval round-trip to a backing store, and is not surfaced in the retrieval response. The chunk contract has no `original_text` field, no `rewritten_text` alias, and no mechanism to return both. | Add an `original_text: str | null` field to the `Chunk` root model. When `tier=3, changed_text=true` is present in `provenance.transformations`, `original_text` MUST be populated with the verbatim pre-rewrite text, and `text` carries the rewritten form. When no Tier 3 rewrite occurred, `original_text` is null. Update the retrieval response (once a response schema is defined) to surface both when a Tier 3 chunk is returned. Update §18.3 test 4 scope: byte-identity test confirms `text == original_text` for all non-Tier-3 chunks, not that `text` is byte-identical to something the test must separately fetch. |
| **C-R8** | spec §15 ("Query returns zero results"); docs/contracts/ (no retrieval response contract) | **major** | **§15 requires distinguishing "no matches" from "filtered to nothing" from "error" in the query response, but no retrieval response schema exists in the design package to implement this distinction.** §15 states: "Query returns zero results — Required behaviour: Distinguish 'no matches' from 'filtered to nothing' from 'error' in the response." The six contracts in docs/contracts/ cover ingestion pipeline boundaries. None defines the retrieval API response envelope. Without a retrieval response schema, the §15 distinction is unimplementable in a verifiable way: different developers will choose different response shapes, and the §18.2 "failure injection" test layer ("every row of the §15 table has a test that asserts the specified behaviour") cannot assert against an unspecified schema. The explain-mode spec (§11.5) lists filters in effect, but explain mode is a debugging tool, not the normal response path. | Define a `RetrievalResponse` schema (either as a seventh contract or as a sub-section of the Chunk contract page). The schema must carry at minimum: `result_set: list[Chunk]` (possibly empty); `zero_result_reason: enum{no_matches, filtered_to_nothing, null} | null` (null when results exist); `error: ErrorEnvelope | null`; `filters_applied: list[FilterDescription]` (to enable distinguishing filtered-to-nothing from no-matches — if all results were excluded by filter, the filter list explains why). Test §18.3's failure injection layer must reference this schema. |
| **C-R9** | contracts/segment-set.md (`ReassemblyRecord`); contracts/segment-set.md (`Segment.text`) | **minor** | **Reassembly semantics are undefined for null-text segments, making the `reassembly_digest` uncomputable for documents containing figures or headings.** `ReassemblyRecord.method = document_order_concat` specifies: "concatenate every segment's source text ordered by `document_order`, including `excluded`/`boilerplate` segments, yielding the parse-level text." `Segment.text` is optional and "Null only for non-text segments (e.g. figure whose caption is separate)." For a document with `figure_region` segments (text=null), `heading` segments that may have no standalone text, concatenation is undefined (concatenate nulls? skip? insert placeholder?). The `reassembly_digest` in the property test (§18.2) would differ across implementations that handle nulls differently. | Specify in `ReassemblyRecord` exactly how null-text segments are handled during reassembly: "Segments with `text=null` contribute an empty string to the concatenation." Add this as a named invariant and a clause in the property test description. This also means the reassembly digest captures text-only content; non-text regions are covered by `covered_region_ids` (the region accounting is already correct). |
| **C-R10** | contracts/parse-result.md (Open Question 1); segment-taxonomy.md §2.1 (`boilerplate` row); ingestion-config.md (`tier1_operations`) | **minor** | **`boilerplate_strip` appears in two conceptually different places with incompatible meanings.** In ingestion-config.md `TransformationSettings.tier1_operations`, `boilerplate_strip` is a per-class Tier 1 operation applied at Build time. In the taxonomy, boilerplate detection happens at Assess time (§6.2: "boilerplate detection reuses dedup machinery") and in the segment signal matrix at Decompose time. If boilerplate detection is an Assess/Decompose concern, then `boilerplate_strip` as a Build-time Tier 1 operation is redundant — the segment is already typed `boilerplate` and tiered before Build. If it is a Build-time operation, it is late and operates on already-typed segments. The two-stage placement is not explained and creates ambiguity about which stage is authoritative for boilerplate classification. | Clarify that boilerplate classification occurs at Decompose (it is a tier assignment signal) and that the `boilerplate_strip` entry in `tier1_operations` refers not to classification but to the decision of whether to embed boilerplate-tiered segments. Rename to `boilerplate_exclude_from_embedding` or equivalent to distinguish it from the detection signal. If the intent is simply "do not embed segments at salience `boilerplate`", express this as a `RetrievalTreatment` setting or a Build-stage filter rule, not as a text-modifying Tier 1 operation. |
| **C-R11** | ingestion-config.md (`config_version` derivation section); spec §10.5 | **minor** | **`retrieval_defaults` and `retrieval_treatment` are excluded from `config_version` with a rationale that conflicts with §10.5's definition of what must trigger a rebuild.** ingestion-config.md states: "Excluded from the hash (do not affect chunk bytes/vectors): `retrieval_defaults` and `retrieval_treatment` (retrieval-time only — changing salience weighting does not invalidate chunks)." §10.5 states: "Config version is part of chunk identity. A chunking or transformation config change invalidates every chunk it produced." The rationale is sound for pure retrieval weights. However, `RetrievalTreatment` includes `confidence_floor`, which IS used at Build time to assign `excluded` tier — affecting which segments produce chunks at all. If `confidence_floor` changes, segments that were previously excluded from embedding should now be embedded (or vice versa), which requires a rebuild. Excluding `confidence_floor` from `config_version` would silently produce stale chunks. | Audit `RetrievalTreatment` for Build-time vs. retrieval-time fields. `confidence_floor` must be included in the `config_version` hash because it governs which segments the Build stage processes. Pure retrieval weights (`salience_weights`, `rerank_eligible`, `strategy`) may safely be excluded. Split `RetrievalTreatment` into `build_treatment` (fields that affect which segments become chunks — included in hash) and `retrieval_treatment` (fields that affect scoring at query time — excluded from hash). |

## Verified sound

The following properties were checked explicitly and found to be correctly designed:

- **§8 provenance field completeness (base path):** All seven §8 required fields are present in the `Provenance` block (contracts/README.md): `source_document_id` + `source_document_version` (identity and version), `source_location` (position), `structural_path` (breadcrumb), `transformations` (ordered list with tier), `confidence` + `ocr_confidence` (score incorporating OCR), `segment_type` + `salience_tier` (type and tier), and `TenancyBlock` (tenancy and permissions). The progressive assembly model (assembled incrementally at Inventory → Parse → Segment → Chunk, finalized at Build) is correctly documented.

- **Inventory → ParseResult → SegmentSet provenance chain:** `document_id` flows from Inventory to ParseResult (`document_id` required), to SegmentSet (`document_id` required), and into chunk ID derivation and `Provenance.source_document_id`. `content_hash` flows from Inventory to ParseResult (`content_hash` required), to SegmentSet (`content_hash` required), and into `Provenance.source_document_version` and chunk ID derivation. `source_region_ids` in each `Segment` and `ExclusionRecord` provides a traceable link back to every `RegionResult.region_id` in the ParseResult, satisfying the "no silent content loss" invariant (§12).

- **OCR confidence propagation:** `PageResult.ocr_confidence` (per-page, retained not thresholded) → `RegionResult.ocr_confidence` (finer-grained) → `Segment.ocr_confidence` (carried from source regions) → `Provenance.ocr_confidence` (on chunk, filterable). The path is complete and unbroken across all four contracts. Per-page confidence is correctly retained as a raw number, never thresholded away (§6.2 MUST).

- **Chunk ID determinism and incremental correctness (§10.5):** The five-component canonical string (`document_id ‖ content_hash ‖ config_version ‖ segment_path ‖ chunk_index`) and the SHA-256 derivation correctly implement all four §10.5 MUSTs: IDs are deterministic; replace-by-document is keyed on `document_id` (not chunk ID), so prior-version chunks are swept regardless of their IDs; orphan detection is post-incremental; `config_version` participates in identity, forcing full rebuild on config change.

- **§4.2 C-3 and C-4 enforcement:** Overview.md provides concrete code-enforced mechanisms (not just design statements) for alias indirection (adapter's search operations accept an alias handle type, never a collection name) and shadow-only writes (`index/` exposes only `create_shadow`/`promote`, no write path targets the alias target). The import-linter check in CI for C-5 is similarly concrete.

- **Embedding model mismatch fail-closed (§15, §18.3 test 7):** provider-abstraction.md §3.3 defines the mismatch check precisely: at query time, `model_id` and `vector_dimensions` from the alias metadata (control plane) are compared against the active provider's declared values. Mismatch → `HTTP 409 EMBEDDING_MODEL_MISMATCH` before any vector search. The check uses alias metadata (not Qdrant internals), making it robust across snapshot/restore cycles. The alias swap atomicity (§4.3 of index-lifecycle.md) ensures there is no window during which the alias points at a collection whose model identity does not match the metadata.

- **Tenancy and permissions block (Phase 0 MUST):** `TenancyBlock` is defined once in contracts/README.md shared blocks and is required on the root of all six contracts. The permission fields (`permission_mode`, `permission_principals`, `permission_fidelity`) are correctly designed for server-side enforcement: they are filterable payload fields, enforced by the retrieval service before any vector search, and not overridable by client-supplied parameters (§11.4).

- **§9.2 provisional-status inseparability:** eval-set.md's `review_status` field has no default (explicitly stated: "yes, NO DEFAULT") so a question cannot be constructed without declaring its review state. The set-level `confidence_level` correctly propagates from question-level status. Imported sets are unambiguously `production_derived` or `imported_eval_set`; generated sets are `provisional` until reviewed. The `generation_method` field is always present and cannot be set to `reviewed` by LLM output (provider-abstraction.md §4.3).

- **Failure semantics completeness for ingestion paths:** index-lifecycle.md §6 maps all §15 ingestion failure rows to named state machine transitions with specified required behaviors. The embedding-provider-unavailable mid-ingestion path (`INGESTING → PAUSED → INGESTING`) preserves resumability via checkpointing plus deterministic chunk IDs (no duplication on resume). The whole-class-failure path escalates correctly (halt + alert vs. single-document failure which records and continues).

- **Secret hygiene in ingestion config (§14.2, §18.3 test 10):** ingestion-config.md `secret_free_attestation: bool (const true)` is a structural guarantee. Provider credentials are referenced by name (not value) in `EmbeddingConfig.provider`. `Tier3Settings.model_ref` is a name, never a secret. `generated_by` in `Augmentation` records model IDs, not credentials. The config export pipeline (provider-abstraction.md §6.3) explicitly strips endpoint URLs and replaces with placeholders.
